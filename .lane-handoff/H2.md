## RULE-EXCEPTION(title-path) applied (tagged in the source)

All three are in `src/game/hero_move.c`, in or next to fn_8012D39C:
1. `heroMoveGetLine` static inline, used once. Rule: single-use helper. Its evidence is the inlined
   BOOL return, materialised in r0 (li r0,0 / li r0,1 / cmpwi r0,0). A clean fix needs a ruling
   that this counts as the "return value routed through a temp" fingerprint, or a second site.
2. `heroMoveSq` static inline. Rule: helper backed only by instruction shape. Retail's sums of
   squares are unfused (fmuls, fmuls, fadds) across the TU: fn_8012B19C, ChkHinderClear, CA84 x2,
   D39C x3, D7F0 x4, DE94 and moveLeader. That is repeated expansion, so the tag may be
   removable. The same helper is now also used in fn_8012CA84 (no separate tag there).
3. `f32 eps = 1e-7f;` in fn_8012D39C. Rule: local holding a constant. Retail computes -eps as
   `fneg` of the loaded 1e-7f. A literal `-1e-7f` folds into a new pool constant, and a
   `const` local or a static const also folds. A clean fix needs a form that keeps the negation
   without the local.

Not an exception, but a judgement call: `HERO_MOVE_ABS` macro and `heroMoveWrapAngle` in fn_8012CA84.
The macro follows retail's double calls; the helper has four expansions.

## Key findings for the whole TU (for the coordinator and lanes H1/H3)

1. **The TU was very likely compiled with `-inline deferred`, with its source in reverse address
   order.** Tested on GC/1.3: `-inline auto,deferred` emits functions in REVERSE source order,
   builds the .sdata2 pool in emission order, and lets any function inline any other.
   Evidence in this TU:
   - updateChat (0x8012C0B4) contains heroMoveCheckEvent's body (0x8012C540, a higher address),
     including its uninitialised result (r30 is stored when there is no person).
   - heroMoveInitEvent and heroMoveTermEvent are inlined into updateChat verbatim.
   - B7c's 7.0f pool anomaly: a static proc1Step that is code-generated but only inlined.
   On the current source, `-inline auto,deferred` changes no score. Linking the TU would mean
   one source in reverse address order. Verify this on the whole TU before relying on it.
2. **HEROMOVE_MEMBER enum typing (from the mangled names) decides the loop shape.**
   - With `HEROMOVE_MEMBER` loop variables and the parameters of getResID and getModel typed
     HEROMOVE_MEMBER, heroMoveInitEvent, heroMoveTermEvent and updateChat all become exact
     (real 0) in a test build. The retyping must cover getResID and getModel;
     heroMoveCheckMember can stay s32.
   - `-opt nostrength` gives the same result for those three but breaks others. That confirms
     the difference is strength reduction folding the base into a pointer IV, which the enum
     type (compared like an unsigned) suppresses.
   - Side effects of retyping the shared helpers: heroMoveMain stays exact with getResID+model
     typed but regresses if heroMoveCheckMember is typed. initFloor drops 99.6 -> 91.5 unless
     its own member variables and helpers (getPos/getRot/setPos) are typed consistently; not
     solved. This is a TU-wide typing pass and should be done once, after H1/H2/H3 merge.
3. `-O4,s` also makes InitEvent and updateChat exact but breaks most others. That is the same
   strength-reduction effect, not proof of a size-optimised TU.
4. **GC/1.3.2**: every hero_move function scores the same as under GC/1.3 except getStep, which
   rises 95.6 -> 99.3. Keep it as a candidate TU compiler version.
