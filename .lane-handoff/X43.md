## In progress: fn_800D258C (exact form found, next step is to apply it)

The unit `gs_render_util_candidate_800D258C` (0x800D258C-0x800D2738) holds
only this function. Retail reloads the 0.0f constant (`lfs f0,lbl_8047C998`)
before each of the three abs() compares. The current source reads the
extern `lbl_8047C998` variable, so MWCC loads it once (CSE).

- These forms are byte-exact (tested in a scratch compile with the
  gs_render_util flags, GC/1.3 `-use_lmw_stmw on -sdata 8 -sdata2 8`):
  - a literal `0.0f` in the compares. This is retail's form: the zero is the
    TU's own pool literal. It can't link as a carve, because the literal
    would be an anonymous `@NN` in the carve's .sdata2. Other linked units
    (gs_render_util_candidate_800D27FC, gs_render_util_exact_800D13C4,
    gs_render_util_exact_800D2B44, ...) reference `lbl_8047C998` by name,
    and `gs_render_util_sdata2.c` owns it.
  - `extern volatile f32 lbl_8047C998;` read in the compares. This is
    linkable and needs a RULE-EXCEPTION tag: "extern stand-in for the TU's
    own pool literal, read as volatile so each compare reloads it".
- The body form doesn't matter. Both of these are exact once the zero reloads:
  - a single reused `f32 a`;
  - `if ((tmp[0] > Z ? tmp[0] : -tmp[0]) < lbl_80478ACC[0] && (tmp[1] ...) && (tmp[2] ...)) c->interest.x = c->interest.x + lbl_8047C9A0;`
- A const-qualified extern does NOT help (33 diffs). Defining
  `const f32 lbl_8047C998 = 0.0f` in the TU gives exact code, but MWCC still
  emits a separate `@NN` literal, so the .sdata2 is wrong.
- Exact next step:
  1. Write a standalone `src/game/gs_render_util_exact_800D258C.c` with
     `fn_800D258C`, the externs it needs and the volatile-extern zero
     (tagged).
  2. Point the configure.py entry at it (CodeCandidate -> Matching).
  3. Run `ninja -j2` and check SHA1.
  4. Run the regression check and commit.
- fn_800D1D00 (gs_render_util.c, 95.87%) has the same transform-update

  jobj's .rodata pool through a base register (`lis/addi rB,lbl_80274AA0`
