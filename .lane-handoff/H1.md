## TU-wide findings (important for the link plan)

1. **Deferred inlining.** Retail cbPoison contains the bodies of heroMoveInitEvent and heroMoveTermEvent, and XD's cbPoison calls both functions. The expansion carries an inline-only copy, `li r30,0; li r24,0; mr r23,r30`, that the standalone InitEvent doesn't have. Its IDs also take r31/r29/r28, the colouring of inlined locals. MWCC inlines a function defined later in the file only with `-inline deferred`. I tested GC/1.0 through 2.6, and deferred mode emits the functions and pools the literals in reverse definition order. So the standalone TU source must:
   - define its functions in reverse address order (fn_80130xxx first, cbTsureFriend last);
   - compile with `-inline auto,deferred`.

   Every other function in the TU compiles to identical code with and without the flag (checked with an instruction diff over all 35 functions).
2. **HEROMOVE_MEMBER enum.** An enum-typed loop counter gives retail's offset strength reduction, where `i*0x20`/`i*4` are kept as offsets and the base is re-added. That is visible in InitEvent/TermEvent/cbPoison. An s32 counter gives pointer strength reduction instead, as in initFloor and heroMoveMain. getResID and getModel take the member as `int`. In a reduced C++ test, HEROMOVE_MEMBER parameters compile exactly like C int parameters, but a C enum parameter does not. The change is neutral for every other function.
3. **`__float_nan`.** `lbl_80478AC0` must be an incomplete array, because all retail uses load it with lis/@l. This is now fixed across hero_move.c.
4. **heroMoveSqrt constants.** heroMoveSqrt must use literal constants (MSL sqrtf: 0.0f, 0.5, 3.0, 0.0). The `lbl_8047D048/50` loads change the float colouring. It now uses the literals, and they pool as @N, as the link plan needs.
