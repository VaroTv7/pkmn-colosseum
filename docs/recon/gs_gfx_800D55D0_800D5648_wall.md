# GSgfx float setters at 0x800D55D0 and 0x800D5648

Both 0x78-byte functions remain at 93.333336% fuzzy match in the canonical
report. The `main/game/gs_gfx_candidate_800D55D0` object is incomplete and
unlinked, so neither function is accepted Recomp source.

The retail/candidate objdiff has the same two-row displacement in each
function: retail emits the `lfs f0, lbl_8047CA30@sda21` before the LR save
`stw r0, 0x14(r1)`; the candidate emits the store before the load. Every
other instruction, including the vararg `crset cr1eq`, branch shape, float
conversion, and calls, aligns. This is a prologue instruction-scheduling wall,
not evidence of different game behavior.

Two source-faithful trials were measured with the owner claimed and the shared
build lock: caching the lower bound in a local retained 93.333336%; splitting
the range condition into two early returns regressed `fn_800D55D0` to
89.666664% by changing branches. Both trials were reverted. The source is
unchanged by this attempt; no assembly or compiler-control workaround was
adopted. Further work needs a source-level shape or compiler-profile insight
that reproduces the retail scheduling without disturbing the rest of the
function and, separately, a complete linked owner object.

## 2026-09-29 (lane D4): resolved, unit linked

The prologue order came from the constants, not from a scheduler setting.
The lower bound, upper bound and scale were extern variables
(`lbl_8047CA30/34/38`). MWCC cannot move a load of an extern variable above
the LR-save store, because the two might alias. A compiler literal can move,
so retail's constants were literals. Written as `0.0f`, `42.5f` and `6.0f`,
both functions match, and MWCC pools the literals in first-use order, as in
retail (0x8047CA30: 0.0f, 42.5f, 6.0f, padding). The `.sdata2` layout also
shows the TU boundaries. The pool 0x8047CA20–0x8047CA30 (0.0f, 640.0f,
480.0f) belongs to fn_800D3FA4's TU, and the pool at 0x8047CA40 belongs to
another TU. The unit now owns `.sdata2` 0x8047CA30–0x8047CA40.
`sdata2_8047C9B0.c` ends at 0x8047CA30, and the rest is in the new
`sdata2_8047CA40.c` (later narrowed to `sdata2_8047CA50.c` when fn_800D85D4 took 0x8047CA40–0x8047CA50). Both functions are 100%, the object links as Matching,
and the retail DOL/REL SHA-1 pass.
