# `fn_8017C8FC` FSYS status-100 mode-0 dispatch

This 0x580-byte retail function is still a text-only `CodeCandidate` in the
FSYS file owner's reconstructed C. The 2026-09-28 baseline report measured
55.946022% fuzzy match; source-faithful data-flow changes raise it to
57.778408% (raw objdiff the same). This is exact-source progress only, not
linked or accepted decompilation progress.

Retail's state-0 scene-read path queries the ARAM cache using
`slot->fileHandle` at offset 0xF8, not a handle read from the archive header.
It also forms the callback's archive data address directly from
`slot->archiveData + entry->dataOffset`, without the candidate's null
fallback. `FSYSScheduleSceneRead` now follows those observed operations.
After that cache query, retail re-resolves the entry by index before checking
its decompressed size, so the mode-0 state-0 source does likewise. The
individual report gains were 55.946022 -> 57.09375 -> 57.778408%.

A re-resolve on the state-4 reload path and removing the outer loop's
null-skip each reduced the report score, so both were reverted. A controlled
unit-wide `-opt level=0` compile without source edits did not close the gap
(raw 55.47443%); the active source also has an earlier optimization-level
setting, so this was diagnostic only. No compiler-control change was retained.

The remaining source is structurally short of retail: the candidate function
has a 0x20-byte frame and 1004-byte body, versus retail's 0xA0-byte frame and
1408-byte body. Retail has separate long compressed and plain mode-2/7
scene-read blocks and explicit entry/temporary homes. The current C still
shares substantial helper/control flow, so its registers, stack slots, and
branch topology differ. Recover those behaviors and the authentic TU/data
ownership before considering a linked `Matching` object; do not pad the
frame or force registers for a score.

Shared-lock `all_source`/report and full `ninja -j2` passed; retail SHA-1
checks passed for `main.dol` and `common_rel.rel`. The currently linked image
does not include this candidate carve.

## Focused second pass: compressed/plain expansion

Retail's compressed-flag branch has two separate 208-byte scene-read blocks.
They query the same cache key, set the same state/status values, and call
`fn_80179FA4` with the same arguments; the observed differences are their
register and stack homes. Spelling those blocks out as separate, identical C
branches produced exactly the same candidate output: this compiler merged
them, so source duplication alone is not evidence for distinct behavior.

Retail also re-derives an entry pointer inside each block. Passing the index
to `FSYSScheduleSceneRead` and re-resolving there was tested, but regressed
the report to 56.383522%; it did not recover the retail branch shape. Both
experiments were reverted. The final second-pass report remains 57.778408%,
still a `CodeCandidate`; the full build and DOL/REL SHA checks passed again.

## Focused fourth pass: scene-read blocks and loop lifetime

The retail mode-2/7 branch has a second archive-entry-table lookup inside
each of its compressed and plain scene-read blocks. The separate blocks each
query `fn_8017F794` with `slot->fileHandle`, the re-resolved entry's group
and name IDs, then either set sub-entry state 4/status 100 or set state 3/
status 301 and call `fn_80179FA4`. Retail reads its archive base and entry
payload offset in each block, and passes that archive-relative address as the
seventh call argument. These observations support the current behavior but
also confirm that the shared `FSYSScheduleSceneRead` abstraction does not
reflect the retail function's local data flow.

An in-function trial spelled out both blocks and re-resolved the entry for
each. It compiled, but reduced the fuzzy score from 57.778408% to
56.383522% (1072-byte candidate versus 1408-byte retail). It was reverted.
Caching `slot->numEntries` before the mode-3 loop, which would reflect the
retail loop's one-time count load, produced byte-identical candidate output
and was also reverted. Neither trial changes the linked acceptance status.

The current candidate's mode-3 loop loaded the count into CTR and used
`bdnz`, whereas retail increments its index, reloads `slot->numEntries`,
and uses `cmplw`/`blt`; the previous description had these sides reversed.
The candidate also maintains a separate four-byte table offset, absent from
retail's visible loop tail. The large mode-2/7 scene blocks remain distinct
in retail, while the candidate's shared shape and compiler settings collapse
them. The next meaningful match pass should reconstruct the original
table-iteration and local-lifetime structure from this control-flow evidence,
not add dummy stack variables or compiler pragmas to force a score.

## Seventh pass: two distinct archive-table offsets

The retail disassembly distinguishes three lookups in the normal state-0
path. The first reads the table offset at `archive + 0x18`. The second, after
the cache query, reads the slot's cached offset at `slot + 0x18` (retail
`lwz r3,0x18(r31)` at function offset `0x234`). The state-4 reload path also
reads `slot + 0x18` before mode dispatch (offset `0x4B8`). The candidate had
used the archive-header offset for the state-0 second lookup and omitted the
reload lookup. Each mode-2/7 scene-read block subsequently re-resolves
through `archive + 0x18` again and takes its size from the preceding entry
while taking the cache key, payload offset and callback entry from this third
lookup. The shared helper had reused the preceding entry for both.

Those source-order and data-source distinctions are now represented directly
in C. Isolating the state-0 second lookup alone scored 58.576706%; including
the reload lookup scored 59.673294%; restoring the distinct scene-read
lookup/size flow raised the guarded canonical report to **60.914772%** from
59.772728%. The score remains far from exact, the object remains a
`CodeCandidate` and is not linked or accepted. In particular, retail still
uses separate long compressed and plain blocks with a 0xA0-byte frame; the
candidate's helper form does not reproduce their full local lifetimes.

## Ninth pass: scene-read homes and mode-3 loop audit

The current guarded objdiff confirms that retail's compressed scene-read
block (`+0x2E0` onward) and plain block (`+0x3C4` onward) are separate, each

and passes the original size. The existing helper already supplies the
observed callback arguments and cache key, while O4,s removes unused homes
and merges the two identical bodies. Adding an otherwise-unused size local

the cache query or that the field is volatile; neither a volatile annotation

two cache-result branches which call the same `fn_8017B6B8`; the candidate's
single call is behaviorally equivalent, and duplicating it without an
independent state effect would only force compiler structure. This bounded
pass found no admissible source correction. The owner SHA-256 remains
